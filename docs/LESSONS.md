# 经验与避坑记录

这份文档记的是「做这个工具时踩到和验证过的东西」，不是使用说明。所有结论都标注了取证环境。

## 1. 先定义「成功」，再写代码

「关掉显示器」有三种完全不同的实现，选错方向会白干：

| 路线 | 效果 | 省电 | 远程观看 | 被顶回来的风险 |
| --- | --- | --- | --- | --- |
| DPMS 硬件关屏（本项目） | 面板真黑 | 是 | 画面可能跟着黑 | 有，取决于驱动和其它程序的显示请求 |
| 全屏黑色遮罩 | 只是看不见 | 否，背光还亮着 | 远程也是黑的 | 无 |
| 锁屏 / 睡眠 | 睡眠会**打断后台任务** | 部分 | 中断 | — |

判据必须写成「**屏幕一直黑到下一次输入**」，而不是「屏幕黑过」。闪一下又亮 = 失败，这是最容易骗过自测的一种假成功。

## 2. DPMS 关屏的正确姿势

- 消息：`WM_SYSCOMMAND (0x0112)` + `wParam = SC_MONITORPOWER (0xF170)` + `lParam = 2`。`lParam` 的 `0=亮、1=低功率、2=关`，别只传 `SC_MONITORPOWER` 而不带 `2`。
- 目标：`HWND_BROADCAST (0xFFFF)`。这条消息靠**每个顶层窗口的默认窗口过程**把它转发给端口/监视器驱动，最终落到显示器电源状态。因此它不需要管理员权限，也和「当前哪个窗口在前台」无关。
- 用 `SendMessageTimeout` 而**不是** `SendMessage`：广播是同步等待，任何一个顶层窗口卡死（挂了的 Electron 程序是常见嫌疑人）就会把你的进程一起拖住。`SMTO_ABORTIFHUNG` + 2000ms 才安全。
- 本项目再补一次 `PostMessage`（异步，不等待）：个别驱动/软件只认其中一种投递方式。默认 `both`，`-method` 可单独试。
- 发送前先 `SetThreadExecutionState(ES_CONTINUOUS)`：清掉**自己线程**的 `ES_DISPLAY_REQUIRED` 请求。注意这是**按线程**的，你清不掉别的进程登记的请求。

## 3. 「别的程序把屏幕顶回来」这件事——实测推翻了我的预期

`powercfg /requests` 的 `DISPLAY:` 段列出的是登记了「显示保持唤醒」的进程，常见来源：视频播放器、会议软件、远程控制（向日葵 AweSun）、部分显卡/扩展坞驱动。它们会让 Windows 的**闲置关屏计时器**永远不触发，这是「人走了屏幕还亮着」的根因。

我原本预计：这台机器上向日葵常驻一条 DISPLAY 请求，手动关屏会被它一秒顶回来，得改用黑色遮罩。

**实测结论相反**（环境：Windows 11 26200 / 单显示器 1920x1080 / 向日葵在跑）：DPMS 关屏生效后**一直黑到动鼠标**，没有被顶回来。也就是说这条请求主要影响「系统自己决定关屏」，对「显式广播关屏」不是硬拦。

所以顺序应该是：**先实测，再决定要不要退到遮罩方案**，不要凭 `powercfg /requests` 的输出判死刑。真遇到黑一下就亮的机器，处置办法是退出第 `[2]` 节列出的那个程序，或者用 `-method broadcast` / `-method post` 各试一次。

## 4. 关屏 ≠ 睡眠，两套设置要分开看

`powercfg /query SCHEME_CURRENT SUB_SLEEP STANDBYIDLE` 输出的「电源设置索引」是**秒**的十六进制：`0x00000000` = 从不，`0x00000258` = 600 秒 = 10 分钟。

本机实测：交流电 = 从不，直流电 = 10 分钟；`powercfg /a` 显示 S3 待机可用。含义是**插电挂机安全，拔电跑长任务会被睡眠打断**。

这个工具刻意**不改电源计划**：改系统配置的影响面比关一次屏大得多，而且用户可能本来就想要睡眠。它只负责报告现值（`scripts/diagnose.ps1`）。

## 5. 不可见的倒计时要给它一个可感知的信号

双击之后有 2 秒缓冲（等你把手从鼠标上拿开）。这 2 秒里屏幕上**什么都没发生**，人的本能是再动一下鼠标确认——于是屏幕点亮，看起来像「这软件坏了」。加一声 `SystemSounds.Exclamation` 作为「倒计时已开始」的信号后，这个误判消失；`-quiet` 可以关掉。

同理，`/target:winexe` 而不是控制台程序：双击时闪出一个黑色控制台窗口，虽然无害，但会让用户怀疑「我是不是启动了别的东西」。

## 6. 打包选型：为什么不是 PyInstaller

这台机器上熟路的是 Python + PyInstaller onedir + Inno Setup 那条链，但这个需求用不上：

- 逻辑只有三个 Win32 API，`csc.exe`（Windows 10/11 自带，实测版本 `4.8.9221.0 / for C# 5`）直接编译成**一个约 10KB 的 exe**，目标机器不需要 Python、不需要 .NET 安装步骤（.NET Framework 4.x 是系统组件）。
- 带图标的窗体/托盘不需要，`MessageBox` 足够显示 `-help`，它来自 `System.Windows.Forms.dll`，而 `csc.rsp` 默认就引用了这个程序集 —— 但本项目仍在 `build.ps1` 里**显式写出 `/r:`**，因为换一台不带默认 rsp 的编译机（或加 `/noconfig`）就会断。
- `/langversion:5`：源码按 C# 5 写，保证老编译机也能过。反面例子是 `Add-Type` 里写 `out _`（C# 7 弃元），Windows PowerShell 5.1 的编译器直接报错。
- **本机自带的 `csc 4.8.9221.0` 不支持 `/deterministic`**（实测报 `fatal error CS2007: 无法识别的选项: '/deterministic+'`）。后果：每次重编 exe 字节都不同（MVID + PE 时间戳会变），**产物哈希只能核对一次，不能靠「重编一遍比哈希」来自证构建没被篡改**。所以本次发版的 exe 只编一次、哈希当场记录、之后所有回核都对着那一份；要复现性只能比源码。
- `/langversion:5`：源码按 C# 5 写，保证老编译机也能过。反面例子是 `Add-Type` 里写 `out _`（C# 7 弃元），Windows PowerShell 5.1 的编译器直接报错。
- `csc` **不支持** `/win32version`，所以 exe 的「文件属性 → 详细信息」里没有版本号。程序集版本通过 `/version:` 注入，`-version` 弹窗读的是它。这一条写在 README 的已知限制里。

## 7. 中文 Windows 的编码坑（做「双击即用」工具时特别容易中）

- `.vbs` 由 WSH 按系统 ANSI 读，**中文注释会直接解析失败**。脚本正文一律 ASCII。
- `.ps1` 里有中文字面量必须是 **UTF-8 with BOM**，否则按 GBK 读成乱码，后果往往不是报错而是「静默执行了错误的内容」——测试假阴性。
- 抓 `powercfg` / `tasklist` 这类 GBK 控制台的中文输出，脚本里要先 `[Console]::OutputEncoding = [Text.Encoding]::GetEncoding(936)` 再调用，否则落盘的是乱码。
- 需要生成**中文文件名**的桌面快捷方式时，用码位拼：`-join ([char]0x5173, [char]0x95ED, ...)`。落盘名字是对的，但控制台把它打印成乱码——**别据乱码判失败**，用 `find ~/Desktop -name "*.lnk" -printf "%f\n"`（git-bash 会正确输出 UTF-8）核对。

## 8. Windows PowerShell 5.1 的 `Add-Type` 限制

`Add-Type -TypeDefinition` 用的是 CodeDom/Roslyn 老路径，`out _`、字符串内插这类 C# 6+ 语法会编译失败，报错形式是「找不到类型」或语法错，容易误判成自己的 P/Invoke 签名写错。写内联 C# 一律按 C# 5 保守风格。另：每次跑 `Add-Type` 都要现场编译（约 1 秒），双击体验上不如预编译 exe —— 这也是最终选 exe 的原因之一。

## 9. 自测方法论：程序侧日志证明不了面板状态

`monitor-off.log` 那类流水只能证明「请求发出去了」，**显示器到底黑没黑只有人眼能确认**。所以这个工具的验收是：跑一次带倒计时的实测，让使用者回答「黑了、一直黑到动鼠标、还是没反应」，再据此决定是否收工或退到遮罩方案。`rc=0` 不等于功能成功。

`scripts/diagnose.ps1` 的输出要按节读：`[2]` 判「谁顶屏」，`[3]` 判「会不会睡着」，`[5]` 判「几块屏」。缺管理员权限时 `[2]` 会返回空而不是报错，这时候「没列出程序」**不能**当成「没有程序顶屏」。

## 10. 发布环境事实（本机）

- GitHub token scope 只有 `repo`/`gist`/`read:org`，**没有 `workflow`** → 本仓库不放 GitHub Actions，构建方式就是本地 `build.ps1`。
- `github.com` 直连超时（curl 15s 不出结果），但 `api.github.com` 返回 200，`ssh -T -p 443 git@ssh.github.com` 能认证。所以：建仓/Release 走 `gh`（API），推 git 对象走 `ssh://git@ssh.github.com:443/...`。
- 推送成功的唯一判据是**本地 HEAD 与远端 SHA 一致**，不是 push 命令返回 0。
- exe 未做代码签名（个人项目无证书）。第一次运行 SmartScreen 可能拦，杀软对这种「广播窗口消息」的小 exe 也可能误报。仓库自带源码和一键构建脚本是对这件事的主要交代，README 里明说。
